# Design decisions, snapshotted

The design lives in a Traycer epic on the maintainer's machine: a decision log
D0 to D23 and a plan set. Nothing outside that machine can open it, and several
of those decisions are corrections that explain why the code looks the way it
does. Issue #28 asks for them to be snapshotted here.

This directory starts that, from the first decision made **after** the epic
stopped being the only copy. Earlier entries are back-filled as they are needed
to explain a change; an entry that is referenced from a commit or a doc and is
missing here is a gap worth closing, not a formality.

One file per decision, `D<n>-<slug>.md`. Each records what was decided, the
reasons, what it replaces, and what it deliberately leaves open. Reasons
outlive picks: a named crate or version goes stale, the criterion that chose it
does not.

| [D36](D36-voice-is-a-server-worker.md) | voice both ways on a server worker, CPU-only today, behind the OpenAI audio shapes; text stays the record and audio is never stored; Parakeet-TDT 0.6B v3 and Kokoro-82M picked against written criteria, measured before final; reverses D30's placement |

| [D39](D39-owner-files.md) | an owner's documents live in the owner's file, attached inside the caller's transaction; the control plane, the index rows and the events stay central; the file carries a marker saying whose it is; a layout, not a throughput change |
| [D40](D40-blobs-on-a-mounted-path.md) | blobs live on the path mounted at the blob root and replication is the mount's job (JuiceFS on TiKV); the S3 driver, Garage and their tier go; the store files stay on local disk |
| [D41](D41-vectors-and-full-text.md) | `fts(path)` and `vector(path, dim)` provision FTS5 and vec0 tables in the owner's file, mirrored by triggers; `storage.query` gains `search` (words, never syntax) and `near`; sqlite-vec is the one `unsafe` in the host, held to hive-db by the gate |
| [D42](D42-local-model-seam.md) | local models behind one seam: four capabilities (read, transcribe, generate, embed) bound to OpenAI-shaped endpoints by configuration, a job queue in the store, `--run-models` as the worker role, the `models` guest capability; the worker writes no document and nothing a model says is trusted |
| [D43](D43-postgres-per-org.md) | the server store returns to Postgres, superseding D38/D39 for the server: one database per organization found through a registry keyed on (org, store generation); the predicate back in the database as functions, row-level security as the second wall from `SET LOCAL` facts `hive-db` sets from the credential; cross-org only by a link set up on both sides and a request to the other side's daemon, never a join; SQLite stays behind `hive-db` as one org, with one suite run against both engines |
| [D44](D44-app-ui-isolation.md) | an app's HTML never runs as the shell: app UI in a sandboxed frame on a per-install origin; where no frame, an allowlist sanitizer drops every `hx-*`/`on*`/script and the host re-adds behaviour only for actions the manifest declares, inside `hx-disable`; the shell's mutating routes check an HMAC capability token keyed on session, verb and route instead of `HX-Request` |
| [D45](D45-offline-shell.md) | supersedes D32 §1: the daemon serves APIs only (user and admin), with no server-rendered UI and no htmx; one Solid.js client does everything, with a complete per-person offline replica in OPFS SQLite that the database never gives up for blobs; blobs are cached under one per-device limit, least recently used evicted first; writes go up as an operation log through the normal write API; last-writer-wins per field on a hybrid logical clock, both versions kept for long text; a hash is never a reference; a bounded offline session, wiped on revocation; apps stay in D44 frames |
| [D46](D46-boards-and-encryption.md) | no org journal; boards (org and personal) hold shared cards, placing is not copying, and emergence is links with backlinks; an item lives in one context, and sharing a private item moves it into the org after a warning; three encryption tiers: a person's own content sealed on their devices with per-field associated data, keys wrapped per device and by a recovery key proved before first use; org backups and blobs under a per-org key; infrastructure at rest; personal documents OCR'd and embedded on the device, org documents on the server; one workspace signed in to every context, with labelled side-by-side panes |
| [D47](D47-the-bus-is-an-item-log.md) | the bus is a log of items addressed to actors, never to processes; a session is an attachment with a cursor; a board is a view of items; deliveries are per session with `queued`, `delivered`, `held` (with reason), `read`, `acted` and `refused`, written by the party that observed each; decisions fan out to every session; push into Claude Code through a `claude/channel` MCP server, a cursor inbox for everything else; `bus.digest` replaces the wake-up board reads; the events table stays the transport and the suite runs with the bell disconnected |
| [D48](D48-the-vault-for-ai-and-humans.md) | the vault has two faces over one store: a human sees owned, versioned items; an AI only ever holds a lease, pinned to actor and principal, injected into tmpfs or environment, recorded on the run, and may ask for a grant it lacks but never read; grants decide in the one enforcement point; org entries under a per-org key wrapped by a master key from outside the database, personal entries device-only unless marked server-leasable in those words; 1Password is a synced driver behind the seam (mirror or two-way, both versions kept on a concurrent secret edit, archive never delete, writes batched under its rate limits), speaking Connect from a guest through egress, and the Private vault it cannot reach is refused with the reason |
| [D49](D49-cross-org-projections.md) | cross-org relations read at local speed: an org's daemon is a client of each linked peer, holding a predicate-filtered projection of exactly what the peer granted (`peer_items`, `peer_placements`, `peer_links`, always `untrusted`, keyed on peer and remote id), kept current by the peer's events through the same sync API devices use and by a reconcile that makes a lost push latency rather than staleness; links, boards, backlinks and search run as local rows with text re-indexed and vectors re-embedded on arrival; writes stay requests to the peer; tier (a) content never projects; nothing is ever joined across databases; amends D43 §4 and D46 §1 |
| [D50](D50-oidc-front-door-with-mfa.md) | OIDC is the only way a human signs in: an org's own identity provider, or the daemon's built-in OpenID provider (`--serve-idp`: code + PKCE, device grant, rotating keys in the vault) when there is none; a second factor is mandatory with no off-switch (passkeys first, TOTP, recovery codes; never SMS or e-mail), required as `amr`/`acr` evidence from external issuers or recorded as `asserted-by-policy`; the ID token is exchanged once at `/credentials` for a device credential pinning `(actor, principal)` and is never itself a credential; step-up re-verifies the second factor for vault reveals, device approval, IdP changes and the share step; AI actors never sign in; first boot ends at factor enrolment |
| [D51](D51-a-key-per-context-the-operator-never-holds.md) | every org and every person gets a context key at sign-up, made on the creating device, wrapped per member device and to a proved recovery key (shares for orgs), never held by the operator in any mode; content is sealed under it by default, with server features through purpose-scoped, time-bounded unlocks or on the device; an org may grant the server a working copy (served mode) and take it back, which rotates the key; rotation is one step with versioned ciphertexts and background re-sealing, automatic on member or device removal and on revocation; bring-your-own-key is a wrapping choice through the D48 vault; amends D46 §2b |
| [D52](D52-org-owned-schema-and-one-storage-interface.md) | sign-up provisions the org's database through D43 §6; the org owns an `org` schema it evolves with planned, versioned forward migrations it authors (platform columns and RLS added and unremovable, policy functions refused); one storage interface over blobs, tables and documents with the same verbs and `{trust, data}` on the guest ABI, the client API and the MCP tools, constrained query forms and never raw SQL, `Guard` deciding before any backend; backends are drivers (native in the workspace, or WASM guests through egress with a vault-leased credential) that an org adds per context and primitive, bound only after passing the host's checked-in conformance suite, keyed on `(org, primitive, generation)`, storing ciphertext in sealed contexts; the S3 driver returns as an added driver and not the default |
| [D53](D53-rust-is-the-framework-apps-are-processes.md) | Rust is the framework and apps are processes in TypeScript on Bun or in Python: one container per install on shared compute under the harness's sandbox (digest-pinned image, no network, the daemon's socket, the egress allowlist, read-only root, cgroup limits), started on first call and stopped when idle; the host dispatches invocations over a per-install unix socket with `{trust, data}`; the app reaches the host only through the one API with an install credential minted and revoked with the container; `@hive/app` and `hive_app` wrap the D52 storage interface as the standard storage library; built-ins are Bun apps; trust is per install because a process cannot be taint-tracked per call; the WASM tier is frozen and not extended; amends D32 §5 and D24's app shape |
| [D54](D54-the-branchable-store-is-the-standard.md) | the branchable store is the platform's standard storage: a Neon project per organization provisioned at sign-up through D43 §6, the registry an always-on project, direct endpoints and never a transaction pooler; `branch`, `reset`, `restore` and friends are storage capabilities on the D52 interface with purposes and TTLs, the pool keyed on `(org, generation, branch)` and a branch credential refused on `main`; `schema.plan` rehearses on a branch and reports the catalogue apply will produce; `hive dev --branch` and agent runs get a branch; sync and projections serve `main` only; plain Postgres and SQLite stay as the fallback whose `Engine` reports the capabilities absent and every surface degrades loudly, proved by a required `neon` CI job beside the plain one; reconnect and re-`LISTEN` after scale-to-zero; a self-hosted engine on the cluster (Garage on the Pis, three safekeepers, a control plane we own) is a later record; amends D43 §1, §6, §7 and D52 §1, §3 |
| [D55](D55-the-kit-is-the-shared-daemon.md) | hive-mind is the standard resource kit for other apps: one shared instance per deployment, each host app registered as a host install with a host profile (the host qualifier on every tool name, surfaces on or off refused at the route, its UI slots, extra egress, its org, `requires: kit` absent by default so a host keeps working with the kit down), a sidecar only when an app ships standalone, the same binary either way; a host's plugins are D53 process apps installed into the host with state in the kit's store per install and the host's own records behind its API with scoped tokens; events on the bus, hook points as `tools` and `cron`; a `ui` manifest block renders a validated schema (every action a tool call into the plugin's process) or a framed mini-app on the per-install origin, validated against the host's slots at install; in-process crates later for Rust hosts through a builder that keeps storage behind `Guard`; nectar is the first consumer (nectar#288) |
